## 二、為何不改 PBKDF2 迭代次數

1. **會直接鎖死用戶**，比「資料消失」更嚴重。`isPasswordHash_()` 只接受 `pbkdf2$<6–7 位數字>$…`
   且 `>= 100000`；改成 10000 之後，新設定／重設的密碼會寫成 `pbkdf2$10000$…`，
   驗證時 `isPasswordHash_` 回 `false` → 該用戶永遠「密碼錯誤」。要拆這個地雷，就得同時把
   雜湊格式的最低迭代數調低，等於放寬整份密碼政策。
2. **登入超時的證據不成立**。在本 repo 以 V8 實測（同一份 bundled `@noble/hashes`）：
   hash 約 0.69 s、hash+verify 約 1.18 s，即單次驗證約 0.5 s；Apps Script 同為 V8，
   即使慢 3–5 倍仍只是 1–3 s，離 6 分鐘執行上限很遠。真正拖慢請求的是逐列 `getDataRange()`
   掃描（`load` 一次掃 8 張表），不是 PBKDF2。
3. **10,000 次對離線攻擊幾乎無保護**。12 萬次本身已低於 OWASP 對 PBKDF2-HMAC-SHA256 的建議；
   再除以 12，只是把「登入慢 1 秒」換成「密碼外洩後即時被破解」。
4. 若確實遇到個別旅團逾時，較安全的做法是：**先量度**該旅團回應時間、檢查 Sheets 列數，
   或把迭代次數做成 Script Property（舊雜湊仍按字串內次數驗證）。這點可以在 CUBBOOK 提供
   實際 timeout 日誌與 Sheet 大小後再議。

## 三、級別（level）資料契約

- 儲存：「其他獎章」**col8 = 級別**，值 `E`／`I`／`A`（初／中／高）；舊列留空 = 整枚徽章。
- 冪等鍵：`(YMIS, 獎章 ID, 級別)`；`A26-E` 這類後綴只在 payload／回應出現，Sheet 內仍是 `A26` + 級別。
- 送交：`requestComplete` 接受 `level: 'E'|'I'|'A'`（亦兼容 `1/2/3`、`初級/中級/高級`）。
- 查詢：`load.otherBadges[ymis]['A26-E'] = {name,date,cert,note,level}`；舊資料仍然是 `['A26']`。
  `getOtherBadges` 亦回傳同一對照表（`otherBadges`）及逐項 `level`／`key`。
- 已核實後再送交同一級：回 `{success:true, duplicate:true, already_verified:true}`，不會多開待批。
- 舊列若有 `[CUB_LEVEL=n]` 備註標記（本專案早期寫法），儲存同一級時會**原地升級**成正式級別欄，
  不會多出一列。
- `data/items.json` **零改動**：49 個 ID、sha256 `44997085…9b5d47` 與 CUBBOOK fixture 一致。

## 六、部署

1. 以新 `Code.gs` 覆蓋旅團 Apps Script，`部署 → 管理部署 → 編輯 → 版本：新版本`。
2. 既有 Sheet **毋須**重跑初始化即可使用級別功能；執行一次 `initializeSheets()`（或 `repairSheets`）
   只會補上「其他獎章」col8「級別」表頭，不會改動任何資料列（有回歸測試鎖住）。
3. 前端 build 2026.11.05.1，`LATEST_RELEASE` 已同步；舊前端連新後端、新前端連舊後端均照常運作。
