## 二、PBKDF2 迭代次數：已下調至 10,000

CUBBOOK 的建議已採納。這樣做在**安全上可接受**，理由：

- 本系統只存旅團進度／出席／活動紀錄，冇身份證、住址、醫療或付款資料，密碼外洩的最大損失是「有人幫你剔錯進度」。
- 密碼政策本身是 **4–8 位**（預設臨時密碼 `1234`）。4 位數字只有 10,000 個組合，
  用 12 萬次還是 1 萬次 KDF，離線爆破都只是「幾分鐘 vs 幾十秒」，KDF 次數實際上擋不到甚麼。
- 因此把成本轉去解決**實際會發生**的問題（Apps Script 登入逾時、回應慢），比守住象徵式的迭代次數更有價值。

### 必須同步修正的地方（CUBBOOK 原文未涵蓋）

原文只叫改第 440 行的常數；**只做這一步會令所有新密碼驗證失敗**，因為 `isPasswordHash_()` 當時要求
`pbkdf2$<6–7 位數字>$…` 且 `>= 100000`。本版一併處理：

| 位置 | 改動 | 原因 |
| :--- | :--- | :--- |
| `PBKDF2_ITERATIONS` | `120000` → `10000` | 依 CUBBOOK 建議 |
| `isPasswordHash_()` | 接受 `\d{3,7}`、下限 `1000` | 否則 `pbkdf2$10000$…` 被當成無效雜湊 → 新密碼永遠登入失敗 |
| `DUMMY_PASSWORD_HASH` | 迭代次數改為 `10000`（digest 不變、仍然不對應任何密碼） | 帳號不存在的路徑要保持**同一成本**，否則一樣有時序差異，而 12 萬次的 dummy 反而更慢 |
| `verifyPassword()` | 不變 | 一律讀字串內記錄的次數，所以舊 120,000 次雜湊照樣登入，毋須重設 |
| `handleLogin` 成功路徑 | 加入「登入時收斂」：雜湊次數 ≠ 現行常數就改寫一次 | 否則舊帳戶**每次都**要付 120,000 次的成本（實測 ~620 ms vs ~48 ms），逾時風險只係由「所有新用戶」變成「所有舊用戶」 |

### 實測（Node／V8，與 Apps Script 同一套 bundled @noble/hashes）

`npm run bench:login`（實際跑 `doPost({action:'login'})`，本 sandbox 為 Node/V8，與 Apps Script 同引擎）：

| 情境 | 耗時（median） |
| :--- | ---: |
| 典型旅團（60 用戶／2,000 進度列／60 token）正確密碼 | ~48–51 ms |
| 同上：錯誤密碼 / 未知帳號 / 已鎖定 / 電郵登入 | ~48–58 ms |
| 大型旅團（600 用戶／6,000 進度列／1,000 token） | ~50–54 ms |
| 舊 120,000 次雜湊帳戶**首次**登入（一次性收斂） | ~620 ms |
| 同一帳戶之後每次登入 | ~48 ms |
| KDF 本身（每次） | 10,000 次 ~52 ms／120,000 次 ~576 ms |

單次成功登入只打 **4 次試算表服務**（`Users` 讀 ×2、`Tokens` 加一列、`Users` 寫 last_login），
真機每程約 10–30 ms，即整個登入大約 0.1–0.5 秒，遠離 Apps Script 6 分鐘上限。

若日後想再調高迭代次數，只需改常數：**驗證永遠跟隨字串內的次數**，不會令現有用戶失效。

## 三、級別（level）資料契約

- 儲存：「其他獎章」**col8 = 級別**，值 `E`／`I`／`A`（初／中／高）；舊列留空 = 整枚徽章。
- 冪等鍵：`(YMIS, 獎章 ID, 級別)`；`A26-E` 這類後綴只在 payload／回應出現，Sheet 內仍是 `A26` + 級別。
- 送交：`requestComplete` 接受 `level: 'E'|'I'|'A'`（亦兼容 `1/2/3`、`初級/中級/高級`）。
- 查詢：`load.otherBadges[ymis]['A26-E'] = {name,date,cert,note,level}`；舊資料仍然是 `['A26']`。
  `getOtherBadges` 亦回傳同一對照表（`otherBadges`）及逐項 `level`／`key`。
- 已核實後再送交同一級：回 `{success:true, duplicate:true, already_verified:true}`，不會多開待批。
- 舊列若有 `[CUB_LEVEL=n]` 備註標記（本專案早期寫法），儲存同一級時會**原地升級**成正式級別欄，
  不會多出一列。
- `data/items.json` **零改動**：49 個 ID、sha256 `44997085…9b5d47` 與 CUBBOOK fixture 一致。

## 六、部署

1. 以新 `Code.gs` 覆蓋旅團 Apps Script，`部署 → 管理部署 → 編輯 → 版本：新版本`。
2. 既有 Sheet **毋須**重跑初始化即可使用級別功能；執行一次 `initializeSheets()`（或 `repairSheets`）
   只會補上「其他獎章」col8「級別」表頭，不會改動任何資料列（有回歸測試鎖住）。
3. 前端 build 2026.11.05.1，`LATEST_RELEASE` 已同步；舊前端連新後端、新前端連舊後端均照常運作。
4. PBKDF2 下調後**毋須重設任何密碼**；舊 120,000 次帳戶會在下次成功登入時自動收斂為 10,000 次（一次性 ~0.6 秒）。回滾到舊 `Code.gs`
   （只認 ≥100000 次）的話，期間改過密碼的帳戶會登入失敗——回滾前請留意。
